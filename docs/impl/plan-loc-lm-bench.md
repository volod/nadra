# loc-lm-bench Handoff Plan

This file holds work that belongs to the downstream corpus consumer, not to this repository. It is
written to be copied into that project and scheduled through its own capability lifecycle. Nothing
here is tracked by this repository's plan gate, and nothing here is scheduled by
[the forward plan](plan.md).

Two services, one semantic layer. Nadra owns acquisition and provenance; the consumer owns Ukrainian
model selection and tuning. They do not integrate through a file format they both hardcode. Nadra
publishes an ontology, and the corpus directory this consumer already reads is one **projection** of
it. Design rationale is in [the acquisition plane design](../design/nadra-acquisition-plane.md).

Paths inside the task blocks are relative to the consumer repository, not to this one, and are
written as plain text rather than links for that reason.

## Why a projection rather than a format

A format agreed between two repositories is a point-to-point mapping. It works until a third
consumer appears, and then there are three mappings to keep in step. There are four consumer areas
in scope, so that outcome is scheduled rather than hypothetical.

Instead, nadra defines a small object model of the acquisition domain and renders a projection per
consumer. The practical consequences for this repository:

- Nothing here needs to know how acquisition works, only what a projected document carries.
- Nothing in nadra needs to know this repository's schema, only how to render into it.
- A field this repository needs later is added to the projection. It is not a change to nadra's
  model, and not a schema change here.

## The acquisition ontology, in brief

Eight object types, aligned to the W3C provenance vocabulary so the model is readable outside either
repository.

| Object | Meaning |
| --- | --- |
| `Source` | A publisher or registry |
| `Determination` | A recorded judgement of a Source's terms: retention, processing, redistribution, with its date |
| `AcquisitionRun` | One batch of fetching |
| `Capture` | An immutable observation of a Source at a moment: target URI, capture time, payload digest |
| `Derivation` | The step turning a Capture into a Document |
| `Document` | Normalized immutable text with a content-derived identity |
| `Span` | A character range within a Document |
| `Operator` | The person accountable for a Determination |

The links that matter to this repository: a `Document` was derived from a `Capture`, a `Capture` was
generated by an `AcquisitionRun` and attributed to a `Source`, a `Document` may be a revision of an
earlier `Document`, and a `Span` sits within a `Document`.

Two properties are load-bearing here. Documents are **append-only**: a changed upstream produces a
new Document linked as a revision, never a rewrite, because gold-set spans are character offsets and
a rewrite would silently invalidate every label pointing into that text. And **character offsets are
the join key** between the two services; chunk identities are internal to this repository and never
cross the seam.

## The corpus projection

This is the contract. It is the rendering of the ontology into the shape this repository reads
today.

### Directory layout

```text
<corpus-root>/
  <doc_id>.md                 normalized document text, UTF-8
  <doc_id>.metadata.json      per-document sidecar
```

One text file and one sidecar per document. No nesting and no index file: this repository's own
ingest produces the manifest and fingerprint it needs.

`doc_id` is derived from the `Capture` payload digest and the `Derivation` normalization version. Two
consequences follow: re-deriving from one Capture always yields the same `doc_id` and byte-identical
text, and a changed upstream yields a different `doc_id` rather than a rewrite.

### Sidecar fields, and where each comes from

Fields this repository already reads:

| Sidecar field | Rendered from |
| --- | --- |
| `language` | `Document.language`, measured from script content rather than assumed from the source |
| `version` | `Derivation.normalization_version` |
| `effective_date` | publication date carried on the `Capture`, absent when the source states none |
| `ingestion_time` | left unset; this repository sets it at its own ingest |
| `source_system` | `AcquisitionRun` identity, never `local` |
| `acl_label` | `Determination.access_class` |

Fields the projection adds, which this repository ignores today and which task `ontology-provenance-fields`
below makes it read:

| Sidecar field | Rendered from |
| --- | --- |
| `source_uri` | `Capture.target_uri` |
| `capture_time` | `Capture.capture_time`, distinct from `ingestion_time` |
| `capture_id` | `Capture` identity, resolvable in nadra's capture store |
| `payload_digest` | `Capture.payload_digest`, of the captured bytes rather than of the local text file |
| `licence` | `Determination.redistribution_class` |
| `acquisition_run_id` | `AcquisitionRun` identity |
| `revision_of` | the earlier `Document` identity when this document is a revision, otherwise absent |

Extra fields are additive. A consumer that does not know a field ignores it, which is why nadra can
render the full projection before any task below lands.

### Invariants

- **Document text is immutable.** Gold-set spans are character offsets into it.
- **Character offsets are the join key.** Chunk identities never cross the seam.
- **Nadra does not chunk.** It renders a document and stops.
- **Provenance is additive.** Nothing in the sidecar alters document text or character offsets.
- **Captures are not redistributed.** Only digests, URIs, offsets and licence facts leave the
  machine, and `licence` is what makes that enforceable on this side.

## Suggested capability

These tasks do not fit the existing corpus and gold-data capabilities cleanly, because none of them
is about gold data as such. A new capability is the cleaner home; attaching them to whichever
capability owns corpus governance today is a judgement for that repository rather than this one.

Proposed registry row:

| Capability | Status | How it is evaluated |
| --- | --- | --- |
| `corpus-provenance` | planned | A gold-set item resolves offline to the capture that produced its source document; a corpus version names the acquisition run that produced it; a revised upstream produces a new document version while existing spans continue to resolve against the previous one; an export refuses material whose licence forbids redistribution, shown by a fixture that fails when the gate is removed |

## Tasks

### Corpus provenance -- `corpus-provenance`

#### ontology-provenance-fields

A scored answer cannot be traced to the source it came from. The governance field set carries no
origin: ingestion time records when this repository ingested a document rather than when the source
was captured, and the source hash covers the local file rather than the captured bytes.

- Serves: `corpus-provenance`
- Agent status: CLEAR
- Dependencies: none.
- User-visible outcome: A gold-set item, and any answer scored against it, resolves to a specific
  capture of a specific URI at a specific time under a recorded licence.
- Scope boundary: In scope is reading `source_uri`, `capture_time`, `capture_id`, `payload_digest`,
  `licence`, `acquisition_run_id` and `revision_of` from the projection sidecar and carrying them
  into chunk metadata and the gold-set provenance field. Out of scope is any change to document text,
  character offsets, or existing field semantics: the addition is additive by construction.
- Data and artifact paths: the corpus governance module and its sidecar reader; the gold-set schema;
  the chunk record metadata path.
- Execution path: widen the governance field set, thread the new fields through the sidecar reader
  into chunk metadata, and widen the gold-set provenance field to carry them.
- Acceptance gates: A fixture corpus carrying the projection sidecar ingests with every field present
  in chunk metadata and in the gold-set provenance field. A corpus carrying none of them still
  ingests unchanged, so the addition breaks no existing bundle.
- Documentation target: the corpus and data-prep area of current-state documentation.

#### revision-semantics

The reuse contract treats an unchanged source hash as a reused document. Upstream sources are
revised, and an in-place update would corrupt every gold-set span pointing into the previous text.

- Serves: `corpus-provenance`
- Agent status: CLEAR
- Dependencies: `ontology-provenance-fields`.
- User-visible outcome: A revised source produces a new document version, and labels written against
  the previous version keep resolving instead of silently pointing at different text.
- Scope boundary: In scope is the revision rule for documents whose source system is an acquisition
  run, its enforcement at ingest, keyed on `revision_of`, and the retention of superseded versions.
  Out of scope is the local-file lane, whose existing reuse behaviour is unchanged.
- Data and artifact paths: the corpus ingest and manifest modules; the superseded-document path.
- Execution path: branch the reuse decision on whether the document originates from an acquisition
  run, and route a revision to a new version rather than a replacement.
- Acceptance gates: Re-ingesting a corpus whose upstream text was revised yields a new document
  version with the previous version retained and its spans still resolving. Attempting an in-place
  update of an acquisition-sourced document fails rather than succeeding quietly.
- Documentation target: the corpus and data-prep area of current-state documentation.

#### corpus-version-binding

A corpus fingerprint identifies a corpus but not what produced it, so a gold set cannot name the
corpus version its source spans are valid against.

- Serves: `corpus-provenance`
- Agent status: CLEAR
- Dependencies: `ontology-provenance-fields`.
- User-visible outcome: A gold set names the corpus version it was built against, and that version
  names the acquisition run behind it, so a bundle can be reproduced rather than approximated.
- Scope boundary: In scope is binding the corpus fingerprint to `acquisition_run_id` and recording
  that binding in gold-set bundles. Out of scope is re-running acquisition, which belongs to the
  producing service.
- Data and artifact paths: the corpus manifest and fingerprint modules; the gold-set bundle record.
- Execution path: record the acquisition run identity alongside the corpus fingerprint and carry it
  into the bundle.
- Acceptance gates: A bundle built on an acquisition-sourced corpus names both the corpus fingerprint
  and the acquisition run. A bundle built on a local corpus records the absence explicitly rather
  than leaving the field blank.
- Documentation target: the corpus and data-prep area of current-state documentation.

#### export-redistribution-gate

The access label covers who may read a document, not whether it may be redistributed. Material
acquired under terms that forbid redistribution can currently leave through an export path.

- Serves: `corpus-provenance`
- Agent status: CLEAR
- Dependencies: `ontology-provenance-fields`.
- User-visible outcome: An export refuses material whose `licence` forbids redistribution, so the
  producing service's local-only rule is enforced where the material could actually leave.
- Scope boundary: In scope is a redistribution check on every export path, keyed on the `licence`
  field the projection carries. Out of scope is making the determination, which is the producing
  service's responsibility, and access control, which the existing label already covers.
- Data and artifact paths: every export and publication path; the `licence` field in document
  metadata.
- Execution path: read the licence class at export time and refuse rather than filter, so a partial
  export cannot be mistaken for a complete one.
- Acceptance gates: A fixture containing one non-redistributable document causes the export to refuse
  with that document named. Removing the gate makes the test fail, so the check is shown to have
  teeth.
- Documentation target: the corpus and data-prep area of current-state documentation.

## Integration tasks

Each names the side that owns it.

#### int-1-pin-the-projection

Owner: both. The corpus projection is stated in one repository and nowhere in the other, so it can
drift on either side without anything noticing.

Write the projection into both repositories, one place each, cross-referenced. The producing side
states what it renders; the consuming side states what it reads. Where they disagree, the consuming
side wins, because it is the one already shipped.

#### int-2-round-trip-fixture

Owner: both, one half each. A committed corpus of roughly twenty documents, rendered by the producing
side and ingested here, exercised in both check suites. The producing half is tracked in
[the forward plan](plan.md) as `roundtrip-fixture`; the consuming half belongs here.

Acceptance on this side: the fixture ingests with every document reported ok, and a deliberate change
to a projected field name fails the check rather than passing silently.

#### int-3-order-of-landing

Owner: this side. Land `ontology-provenance-fields` and `revision-semantics` before any gold set is
drafted on acquired material. Both change what a gold-set item means, so drafting first means
drafting twice.

#### int-4-remaining-order

Owner: this side. `corpus-version-binding` and `export-redistribution-gate` follow, in either order.
Neither invalidates existing labels, so neither gates gold-set work.

## Sequencing

Acquisition does not wait on any of this. The producing side's first slice completes against the
projection as this repository reads it today, because unknown sidecar fields are ignored rather than
rejected.

What these tasks buy is a provenance chain that survives end to end. Without them, a scored answer
traces to a corpus document and stops there. With them, it traces through the projection to a capture
of a named URI, at a known time, under a recorded licence, produced by a named acquisition run.
